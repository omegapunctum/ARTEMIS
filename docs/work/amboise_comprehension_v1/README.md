## Вопрос

Может ли человек в уже опубликованном прототипе самостоятельно найти локальный контекст резиденции Кло-Люсе, объяснить совпадение по времени и отличить его от доказанного участия Леонардо? Дополнительно: доступны ли основания и понятны ли пределы даты/отображения?

Эта диагностика не проверяет H1–H8 целиком. Один случай не измеряет преимущество карты перед текстом, глобальную одновременность, историческую истину, весь source workflow, физические устройства или удержание пользователей.

## Подготовка перед будущим запуском

1. Сохранить отдельную запись запуска с authority, вопросом, одной сессией и stop. Не менять старые Gate E результаты.
2. Пригласить взрослого добровольца, не работавшего над реализацией; убедиться, что язык заданий понятен. Получить согласие на обезличенную запись ответов. Не собирать имя, контакты, голос или видео. Отказ прекращает сессию без оценивания.
3. Закрепить commit комплекта, неизменяемый адрес эталона и фактически загруженный build. Именованный release `429b25ef…`/Pages `40465572963` — исторический receipt, не гарантия текущего live build. До сессии модератор проверяет `/ARTEMIS/globe/build-meta.json` и наличие Амбуаза; если build нельзя установить или контекст отсутствует, сбор остановить и записать preflight blocker. Не исправлять интерфейс между заданиями одной сессии.
4. Открыть [стартовый вид](https://omegapunctum.github.io/ARTEMIS/globe/?mode=scrub&at=1518&presence=presence-leonardo-amboise-clos-luce-1516-1519&lang=ru&view=map). 2D выбран для узкой диагностики понимания, а не проверки ценности Globe. Записать UTC, устройство, browser/version, viewport, URL и source SHA/build identity. Идентификатор текущего build берётся из фактического metadata, а не из этой ссылки.
5. Показать только лист участника. Не открывать детали за него, не объяснять кнопки и не читать эталон. Предупредить, что проверяется продукт, а не знание истории человеком. Для поиска участник может использовать текущий интерфейс и его источники.

## Проведение

Читать T1–T5 последовательно, сохраняя фактические слова и действия до интерпретации. Не давать ответов и не задавать наводящие уточнения. Время не ограничено порогом успешности; записывать фактическую длительность, паузы и добровольный отказ. Помощь давать только после фиксации первой попытки и по согласию участника; сохранять точную подсказку и не превращать assisted completion в unaided PASS.

Порядок диагностический: первые задания влияют на последующие. Поэтому результаты — последовательная работа одного человека, а не пять независимых измерений. Если помощь на T1 раскрыла источник или содержание, отметить её влияние на все затронутые последующие ответы. Такой ответ не считается самостоятельно найденным только потому, что подсказку дали раньше.

После последней попытки можно показать эталон и спросить, что осталось непонятно. Отделить этот разбор от наблюдений до подсказок. Не менять задним числом формулировку задачи или рубрику.

## Оценивание и результат

Для каждого задания: `PASS` — критерий выполнен без помощи, включая отсутствие влияющей предыдущей подсказки; `ASSISTED` — выполнен после помощи; `FAIL` — есть противоречащий ответ или действие/объяснение не получено после попытки; `NOT_RUN` — попытки не было. Фактическую причину и помощь сохранять. Если действие выполнено, но объяснение неверно, не ставить PASS.

Критическая ошибка доверия — положительное утверждение о доказанном участии/непрерывном местонахождении, установленном точном дне при нерешённом календаре, длительности в год или историческом отсутствии из-за неотображения. Не считать сам вопрос «мог ли участвовать?» ошибкой: проверяется выданный за факт вывод. Отдельно фиксировать, подтверждает ли интерфейс источник ошибки или это пока лишь интерпретация наблюдателя.

Итог одной сессии:

| Наблюдение | Допустимый вывод |
|---|---|
| Все задания PASS, критических ошибок нет | Диагностический цикл выполнен одним человеком; можно предложить подготовку сравнения. Пользовательская ценность не валидирована |
| ASSISTED/FAIL или критическая ошибка | Есть конкретная трудность; классифицировать interaction / comprehension / content-evidence / protocol; предложить один bounded fix либо уточнение протокола |
| NOT_RUN, недоказанный build, нарушенный порядок или утечка рубрики | Данных недостаточно; обозначить затронутые задания и не делать положительного заключения |

Никакой исход не открывает реализацию автоматически. Ретест после подсказки не доказывает первоначальную понятность; для этого нужен новый новичок. Stop — один разбор фактических наблюдений с ограничениями и одним предложением следующего решения. Не повторять историческую общую приёмку интерфейса без конкретного finding.

## Линейный вариант и будущее сравнение

Эталон уже содержит source-relative резиденцию, событие, обе трактовки календаря, основания и ограничения без синхронизированной карты. Он пригоден для сверки ответов и последующего конструирования baseline. **Он не содержит все 11 Presence, Roman/Architecture слои и весь технический provenance Explorer.** Сравнивать весь свободно доступный Explorer с этим коротким текстом и объявлять доказанное преимущество нельзя.

Перед любым сравнительным сбором отдельный протокол должен определить равный доступный корпус, information parity по каждой оцениваемой Claim/uncertainty/source, сопоставимую навигационную нагрузку, язык, время, условия доступа к внешним страницам, способ распределения участников и критерий сигнала до просмотра ответов. Повторное предъявление того же случая одному человеку создаёт перенос знания; его нельзя убрать одним чередованием порядка. До решения этих вопросов сравнительная часть — `NOT READY / NOT RUN`.

В публичный репозиторий допускается только отдельно проверенный обезличенный итог. Не загружать сырые ответы и рабочие формы автоматически: свободный текст может содержать личные сведения. Текущий комплект содержит только пустой шаблон.
